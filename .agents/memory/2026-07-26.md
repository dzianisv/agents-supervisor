## ⚠️ SELF-INFLICTED CONSENT BUG — and the trap that caused it

PR #195 wired the **Mystic Tarot** page to the existing `PlayTesterSignup` → `POST /api/play-tester`. That endpoint is **AgentPod Mobile-scoped**:

- `apps/agentlabs/app/api/play-tester/route.ts:21` → `addContactToBrevo(email, agentPodListId(), "play-tester")`
- `apps/agentlabs/lib/brevo-contact.ts:68` → `agentPodListId()` = `BREVO_AGENTPOD_LIST_ID`
- `route.ts:7` → `PLAY_OPT_IN_URL = https://play.google.com/apps/internaltest/4701574809387172305`
- Confirmed by `vibebrowser/VibeBrowserProductPage/.agents/memory/2026-07-23.md:5` — Brevo list 9 "AgentPod Mobile", Google Group `beta-testers@agentlabs.cc`

Result: visitors arriving for an AI tarot app were being added to a different product's mailing list and pointed at a different product's internal-test track. **Misleading collection of personal data.** Reverted same day; Tarot page returned to an honest static "closed testing" status with no email capture. `/mobile` (the legitimate AgentPod consumer) untouched.

**Mystic Tarot's real internal-test track ID is UNKNOWN** — it lives in Play Console and must never be guessed. Follow-up issue opened to parameterize the route per product (own Brevo list + own track).

### Lesson
"Reuse the existing component" is not free. A signup endpoint carries a **destination** — a mailing list, a track, a consent scope — and reusing it silently re-points a promise made to one audience at another product's data store. **Before reusing any capture endpoint, trace where the data lands, not just whether the handler returns 200.** The agent that shipped it flagged the doubt itself in its closing line; the flag was correct and I should have required that check up front rather than catching it after deploy.
